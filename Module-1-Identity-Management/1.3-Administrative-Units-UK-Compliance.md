# Runbook 1.3: Geographic Administrative Isolation via Administrative Units

## 1. THE ARCHITECTURAL "WHY"
In a typical UK enterprise architecture spanning multiple corporate hubs (e.g., London and Edinburgh), granting a regional helpdesk engineer tenant-wide administrative privileges violates the Principle of Least Privilege and introduces a catastrophic blast radius. If an attacker compromises a regional helpdesk identity, they inherit lateral modification rights over the entire tenant, including senior executives and critical service principals.

By implementing **Administrative Units (AUs)**, we construct a hard logical perimeter around regional objects. This ensures that the Edinburgh Helpdesk can only modify accounts natively assigned to the Edinburgh business unit, mitigating the risk of lateral escalation while ensuring compliance with UK GDPR data localization and internal governance boundaries.

## 2. THE EXACT CLICK PATH
Follow this exact sequence within the Microsoft Entra admin center to deploy the isolated boundary:

1. Navigate to **`https://entra.microsoft.com`** and authenticate with Global Administrator credentials.
2. Expand **Identity** on the left navigation menu -> click **Roles & admins** -> select **Administrative units**.
3. Click **+ Add**.
4. In the **Basics** tab, populate the fields
   * **Name:** `UK-Edinburgh-Operations-AU`
   * **Description:** `Logical boundary enclosing all Edinburgh-based operational personnel and regional helpdesk assignment.`
5. Click **Review + create**, then click **Create**.
6. Select the newly created `UK-Edinburgh-Operations-AU` from the list.
7. Under **Manage**, click **Members** -> click **+ Add member** -> search for and select `Edin-User-01` -> click **Select**.
8. Under **Manage**, click **Roles and administrators** -> select the **Helpdesk Administrator** role.
9. Click **+ Add assignments** -> search for and select `Edin-Helpdesk` -> click **Add**.

## 3. THE EXAM STRATAGEM & TRAPS
When sitting the SC-300 exam, Microsoft routinely tests your ability to distinguish between **Security Group scoping** and **Administrative Unit scoping**.

* **The Trap:** A scenario asks you to delegate the ability to reset passwords for users in a specific department to a localized administrator. The options will include: *"Assign the Helpdesk Administrator role to a security group containing the local administrators, and add the target users to that group."*
* **The Reality:** This is a distractor. Standard Entra ID roles cannot be scoped natively via standard security group memberships to limit the *target* of the administrative action. 
* **The Correct Answer:** The target users must reside inside an Administrative Unit, and the administrative role assignment must be explicitly scoped to that specific Administrative Unit container.


## 4. THE LIVE LAB ASSIGNMENT & VALIDATION

### Scenario Setup
Create a test architecture within your Microsoft 365 E5 trial tenant matching the steps above. You must have:
* One target user (`Edin-User-01`) placed inside `UK-Edinburgh-Operations-AU`.
* One helpdesk user (`Edin-Helpdesk`) assigned the Helpdesk Administrator role scoped *only* to that AU.
* One external user or global admin account completely outside the AU.

### Validation Testing Execution
1. Open an InPrivate browser session and log into `entra.microsoft.com` using the `Edin-Helpdesk` account.
2. Navigate to **Identity** -> **Users** -> **All users**.
3. Select `Edin-User-01`, and click **Reset password**. Note the outcome.
4. Return to **All users**, select your root Global Administrator account, and click **Reset password**. Note the outcome.
